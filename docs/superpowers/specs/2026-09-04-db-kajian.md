# DB Kajian — Keep vs Jsonb (Plan 3.2)

Bench: `bash apps/api-rs/scripts/bench.sh` on live `plane-db` (dev data:
1 project, 0 issues — timings are planning-dominated).

## Evidence

- Keep (normalized): `issues` filtered by `project_id` + `archived_at IS NULL`
  uses existing btree `issue_project_id_fea0fc80`; exec ~0.15–0.2 ms.
- `priority` is already a plain `varchar` column — the plan's hypothetical
  `properties->>'priority'` jsonb path does not apply: **no `properties`
  column exists**. A jsonb migration would be a full schema rewrite for
  zero demonstrated win, plus ~15% GIN size overhead.
- `issues` total 80 kB / indexes 72 kB — no size pressure.
- Gap found: no composite index on the hot list filter
  `(project_id, archived_at)` → added `0002_issue_project_archived_idx.sql`.

## Decision

**Keep current normalized schema.** Tune: pool 10→5
(`crates/common/src/db.rs`), PG `max_connections` 1000→100
(`docker-compose.yml`), new composite index above.
